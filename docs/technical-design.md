# SIKMUBYNCH 기술 설계

## 목표

기술 설계의 목적은 대규모 호드, 실시간 건설, 반복 런 구조를 안정적으로 지탱하는 것이다. 구현은 플레이 약속을 기준으로 한다. 성능, UI, 데이터 구조, 시스템 경계는 “수천 단위의 적이 보이는 상황에서 플레이어가 **어디서 얼마나 몰려오는지**와 **방어선이 어디서 무너지는지**를 판단할 수 있는가”를 중심으로 결정한다.

## 기술 결정

2026-09-16에 아래 세 가지를 확정했다. 이후의 기술 논의는 이 결정을 전제로 한다.

| 결정 | 내용 | 이유 |
| --- | --- | --- |
| 게임 방향 유지 | 엄청난 물량이 몰려오고, 플레이어가 건설과 배치로 방어선을 유지한다 | 압박감, 배치 판단, 대량 전투 피드백, 반복성이라는 핵심 가치는 그대로 유효하다. 아이디어를 버릴 이유가 없다 |
| 2D 쿼터뷰로 전환 | 3D 모델과 3D 카메라를 버리고, 2D 쿼터뷰 스프라이트로 그린다 | 이 게임에서 중요한 것은 모델 디테일이 아니라 적의 방향·규모와 방어선 붕괴 지점의 가독성이다. 1만 단위 물량을 목표로 하면 3D는 얻는 것보다 부담이 크다 |
| Godot 유지 | 엔진을 바꾸지 않는다. 단, 모든 것을 Node로 만들지 않는다 | 첫 게임 개발에서는 엔진 교체보다 게임을 완성하는 데 집중한다. 물량은 엔진이 아니라 시뮬레이션과 렌더러의 분리로 해결한다 |

2026-09-21에 범위와 순서를 추가로 확정했다.

| 결정 | 내용 | 이유 |
| --- | --- | --- |
| 게임은 작게, 아키텍처는 크게 | 첫 프로토타입은 100~500마리, 구조는 10,000마리까지 확장 가능하게 | 처음부터 10,000을 만들 필요는 없다. 재미는 작은 물량에서 먼저 확인하고, 구조만 크게 잡는다 |
| 보류 시스템 제거 | 증강·보상 카드·시너지·이벤트·유닛·메타를 첫 프로토타입에서 뺀다 | 핵심 전투가 재미있는지 확인하기 전에 너무 많은 시스템이 올라가 있었다. 전환 대상이 줄어 기반 작업도 가벼워진다 |
| 단계적 물량 | 100 → 500 → 1,000 → 5,000 → 10,000 | 각 단계에서 실제 병목을 측정하고 올라간다 |
| C++은 탈출구 | GDScript + 좋은 데이터 구조 → 프로파일러 → 병목 발견 → 필요한 부분만 GDExtension | 처음부터 C++로 만들지 않는다. 측정 없이 최적화하지 않는다 |

“2D”는 평면 탑다운이 아니다. 시점은 기존 비주얼 방향인 이소메트릭을 유지한 **쿼터뷰**이고, 바뀌는 것은 화면을 그리는 방식뿐이다. 평면 탑다운에 색상 도형을 놓는 방식은 이미 한 번 기각됐다.

## 엔진과 렌더링

- **엔진**: Godot 4
- **언어**: GDScript. 시뮬레이션 핵심 루프는 PackedArray 기반 데이터 지향 코드로 작성한다
- **시점**: 2D 쿼터뷰, 2:1 이소메트릭 타일 기준, `Camera2D`
- **렌더링**: 2D 캔버스. 대량 개체는 MultiMesh 또는 RenderingServer 직접 호출로 배칭한다
- **렌더러**: GL Compatibility
- **플랫폼**: Windows PC 우선

Godot은 빠른 프로토타이핑, 작은 빌드 크기, 데이터와 씬 편집 편의성이 장점이다. 반대로 개체마다 Node를 만드는 방식은 수천 단위에서 병목이 된다. 그래서 Node는 건물·UI처럼 수가 적은 대상에만 쓰고, 적·발사체·이펙트는 Node 없이 배열로 다룬다.

## 핵심 구조: 시뮬레이션과 렌더러 분리

```text
                     Game Simulation
                     (고정 틱, Node 없음)
                            │
          ┌─────────────────┼─────────────────┐
          ↓                 ↓                 ↓
      Enemy Sim        Combat Sim         Wave Sim
   (적 상태 배열)     (타겟·피해·감속)     (규모·방향·큐)
          │                 │                 │
      Flow Field       Spatial Grid        Spawner
          │                 │                 │
          └─────────────────┼─────────────────┘
                            ↓
                        Renderer
                (시뮬레이션 상태를 읽어 배칭 그리기)
                            ↓
                         2D 화면
              (쿼터뷰 스프라이트, HUD, 레이더)
```

### 계층 규칙

1. **시뮬레이션은 Node를 모른다.** 게임 상태는 `PackedFloat32Array`, `PackedInt32Array` 같은 배열과 인덱스로 저장한다. 시뮬레이션 코드는 Node를 참조하거나 `queue_free`를 호출하지 않는다.
2. **렌더러는 읽기만 한다.** 시뮬레이션 상태를 읽어 그리며, 게임 규칙을 바꾸지 않는다.
3. **Node 허용 범위는 건물, HQ, UI다.** 적, 발사체, 이펙트는 Node가 아니라 시뮬레이션 배열의 인덱스다. 유닛을 재도입하면 같은 규칙을 따른다.
4. **시뮬레이션은 고정 틱으로 돈다.** 렌더러는 프레임마다 마지막 두 틱 사이를 보간한다.
5. **시뮬레이션은 재현 가능해야 한다.** 같은 seed와 같은 입력이면 같은 결과가 나오며, 렌더러 없이 headless로 실행할 수 있다.
6. **풀링은 별도 시스템이 아니다.** 배열과 free list가 곧 풀이다. 개체 생성·소멸은 인덱스 할당·반납이다.
7. **첫 프로토타입에 없는 시스템의 자리를 미리 만들지 않는다.** 시너지 배율 테이블, 이벤트 훅, 유닛 배열은 재도입할 때 추가한다. 다만 Combat Sim의 피해 계산은 한곳을 거치게 해서 나중에 배율을 끼울 수 있게 한다.

### 계층별 책임

| 계층 | 책임 | 책임 밖 |
| --- | --- | --- |
| Game Simulation | 고정 틱 진행, 하위 Sim 호출 순서, 런 상태 스냅샷, 정지·배속 | 그리기, 입력 해석 |
| Enemy Sim | 적 위치·HP·속도·감속 배열, Flow Field 방향 적용, 건물 접촉·공격 판정, 사망 처리와 분열 예약 | 스폰 결정, 피해 계산 규칙 |
| Combat Sim | 타워 타겟팅, 발사체 진행, 피해와 감속 적용, 처치 이벤트 발행 | 적 이동, 유입 규모 |
| Wave Sim | 시간 기반 유입률, 압박 배율·방향 가중치 드리프트, 구성, 스폰 위치(진입로·넓어지는 링). 웨이브·급증·완료 판정 없음 | 개체 생성 자체, UI 경고 |
| Flow Field | 적 집단 이동 방향 필드, 장애물 점유 카운트, 재계산 분산 | 전투 판정, 스폰 정책 |
| Spatial Grid | 셀 기반 근접 탐색, 인덱스 단위 등록·이동·해제 | 게임 규칙 결정 |
| Spawner | 이번 틱 스폰 수 소비, Enemy Sim에 개체 추가 (Wave Sim의 drain_spawns) | 유입 수식 |
| Renderer | 적·발사체·이펙트 배칭 그리기, 보간, 피격·처치 시각 피드백, 카메라 | 상태 변경 |

기존 코드는 아래처럼 정리한다. 보류 시스템은 새 구조로 옮기지 않고 제거한다.

| 기존 | 처리 | 변화 |
| --- | --- | --- |
| GameManager | Autoload 유지 | 런 상태, 자원, 킬 카운트를 Game Simulation 결과로 갱신 |
| WaveDirector | Wave Sim 계산부로 이관 | 이미 순수 계산에 가깝다. 스폰 큐를 Wave Sim으로 옮기고 정예·이벤트 배율은 뺀다 |
| FlowField | Enemy Sim 입력으로 이관 | Autoload에서 시뮬레이션 소유 객체로 이동, 2D 격자 좌표 |
| SpatialGrid | Combat Sim 내부로 이관 | Node 참조 대신 개체 인덱스 저장 |
| GameFeel, EffectsManager, AudioManager | 표현 계층 유지 | 시뮬레이션 이벤트를 구독해 쉐이크·이펙트·사운드 재생 |
| GameUIController, ThreatRadar | 표현 계층 유지 | 시뮬레이션 스냅샷을 읽어 HUD·레이더 갱신. 카드·시너지 UI는 제거 |
| 적·발사체 씬 | 제거 | 씬 대신 Enemy Sim·Combat Sim 배열과 Renderer |
| 건물 씬 (HQ, 바리케이드, 타워) | 2D Node로 재구성 | `Sprite2D` 기반, 수십 개 규모라 Node 유지. 타워는 3종으로 분화 |
| SynergyManager, EventManager, RewardCard, TraitData | 제거 (보류) | 재도입 시 시뮬레이션 구조에 맞춰 다시 설계 |
| 유닛 씬, UnitData, 배럭, 채굴기, 버프 타워, 미네랄 오브 | 제거 (보류) | 재도입 시 유닛은 시뮬레이션 배열로 |
| 3D 씬, GLB 모델, 3D 제작 도구 | 제거 | 2D 아트 가이드의 스프라이트로 대체 |

제거되는 코드는 커밋 이력에 남는다. 재도입할 때 참고는 하되 그대로 되살리지 않는다.

### 틱과 프레임

- 시뮬레이션 틱: 고정 30Hz로 시작한다. 병목이 확인되면 20Hz까지 낮추고 보간으로 감춘다.
- 업데이트 분산: 화면 밖이나 방어선에서 먼 적은 N틱마다 갱신한다. 가까운 전투의 정확도는 유지한다.
- 렌더 프레임: 60fps 목표. 시뮬레이션이 느려져도 카메라·UI·보간은 끊기지 않는다.
- 정지·배속: 시뮬레이션 틱 호출을 멈추거나 배수로 호출한다. `Engine.time_scale`에 의존하지 않는다.

### 데이터 저장 형태

Enemy Sim을 예로 든 최소 구성이다. Combat Sim의 발사체도 같은 형태를 따른다.

```text
pos_x, pos_y        PackedFloat32Array   # 월드 좌표
prev_x, prev_y      PackedFloat32Array   # 렌더 보간용 직전 틱 좌표
hp                  PackedFloat32Array
type_id             PackedInt32Array     # EnemyData 조회 인덱스
slow_timer          PackedFloat32Array   # 감속 타이머 (상태 이상이 늘면 배열을 추가)
flags               PackedInt32Array     # 생존, 분열 예약 등 비트
free_list           PackedInt32Array     # 반납된 인덱스
alive_count         int
```

타입별 데이터(`EnemyData`, `BuildingData`)는 Resource로 유지하되, 시뮬레이션은 시작 시 이를 배열 테이블로 펼쳐 인덱스로 조회한다.

### 렌더러

- 적·발사체·이펙트: 타입별 `MultiMeshInstance2D` 1개와 아틀라스 1장. 매 프레임 transform과 custom data(색, 프레임 인덱스)만 갱신한다.
- 건물·HQ: `Sprite2D` Node. 수십 개 규모라 개별 Node가 문제되지 않는다.
- 깊이 정렬: 쿼터뷰 깊이는 y 기준이다. MultiMesh 내부는 정렬되지 않으므로 레이어 순서(지면 → 그림자 → 건물·적 → 발사체 → 이펙트 → UI)로 해결한다. 큰 개체(정예·보스)를 재도입하면 별도 처리한다.
- HP 바: 건물만 표시한다. 적은 색 변화로 피격을 보여준다.
- 피격·처치 피드백: 시뮬레이션이 발행한 이벤트 큐를 렌더러가 소비한다. 대량 처치 시 이펙트 수는 상한을 두고 병합한다. 포격 폭발은 반경 안의 처치를 하나의 이벤트로 묶는다.

## 3D에서 2D로 전환하는 순서

현재 프로토타입은 3D이며 적마다 `CharacterBody3D`와 여러 `MeshInstance3D`를 쓴다. 범위를 축소했으므로 기존 코드를 조금씩 고치는 대신 `sim/`과 `render/`를 새로 만들고, 기존 코드에서 순수 계산(웨이브 수식, Flow Field 알고리즘, 건물 데이터)만 옮긴다. 각 단계는 동작 확인과 성능 측정을 함께 한다.

1. `sim/`에 Enemy Sim, Flow Field, Spatial Grid, Wave Sim을 새로 작성한다. 렌더러 없이 headless로 100마리가 본진을 향해 움직이는 것을 확인한다.
2. `render/`에 MultiMesh 2D 렌더러와 쿼터뷰 카메라를 만든다. 폴백 스프라이트(색상 마름모)로 100마리를 그린 뒤 500마리까지 올린다.
3. 건물(HQ, 방어물 1~2, 타워 3)을 2D Node로 재구성하고 배치·철거를 붙인다. Flow Field가 건물을 장애물로 반영하는지 확인한다.
4. Combat Sim으로 타워 3종의 타겟팅, 발사체, 피해, 감속을 만든다. 시너지 배율은 없다.
5. HQ 파괴 → 게임오버 → 재시작과 최소 HUD를 붙여 런이 끝까지 돌게 한다.
6. 3D 씬, GLB, 3D 제작 도구, 보류 시스템 코드를 제거한다.
7. 회귀 검증을 렌더러 없는 시뮬레이션 실행 기준으로 다시 작성한다.

전환 중에는 새 게임플레이 기능을 추가하지 않는다. 첫 프로토타입 범위 밖의 것은 “나중에 넣기 쉽게” 만들려고 미리 구조를 늘리지도 않는다.

## 압박 스트림 구현

압박은 Wave Sim(`sim/wave_sim.gd`)이 순수 계산으로 관리한다. 웨이브·급증·휴식·카운트다운·완료 판정은 없다. 런 시작부터 끝까지 한 흐름으로 몰려오며, 실제 개체 추가는 `drain_spawns()`가 Enemy Sim에 넘긴다. 호출처 호환을 위해 파일·필드 이름(`waves`)은 유지한다.

유입은 두 겹이다.

- **바닥 유입**: 초당 스폰 수 = `base_rate(경과 시간) × pressure`. 방어가 약하면 이것만으로 넘친다.
- **무리 유지(디렉터)**: 살아 있는 적 수가 `target_alive(경과 시간)`보다 적으면 부족분을 약 2초에 걸쳐 채운다. 처치 보상 경제에서는 방어력이 누적 처치에 비례해 커지므로, 시간 곡선만으로는 몇 분 만에 따라잡혀 화면이 빈다. 디렉터가 “방어가 강할수록 빨리 채운다”로 이를 막는다. 목표 무리 수는 0분 60 → 5분 560 → 10분 1,460으로 계속 오른다.

변주는 예고 없이 천천히 떠도는 값으로만 만든다.

- **압박 배율**: 0.9~1.5 사이를 떠돈다. 바닥이 0.9라 잦아드는 구간이 없고, 정점은 예고 없이 온다.
- **변 가중치**: 항상 사방에서 오되 한동안 한쪽이 더 두껍다. 두꺼운 변은 위협 레이더에 표시한다.
- **진입로**: 변마다 3개가 천천히 옮겨 다녀 스폰이 기둥처럼 모인다.
- **스폰 링**: 본진 주변에서 시작해 기본 줌 화면 바로 바깥(32타일)까지 넓어진다. 걸어오는 무리가 보인다.
- **개체 강화**: HP·공격력·속도 배율과 구성 비율(러셔·탱크·스플리터)은 경과 시간의 함수다.

수식과 상수는 코드 머리말이 기준이며, 조정 근거가 된 플레이 판단도 거기에 남긴다.

## 적 처리와 성능

대규모 적 처리는 다음 원칙을 따른다.

- 적·발사체는 Node가 아니라 배열 인덱스다.
- 근접 탐색은 전역 스캔 대신 Spatial Grid를 사용한다.
- 경로는 개별 A* 대신 Flow Field를 공유한다.
- 그리기는 타입별 MultiMesh로 배칭한다. 개체 수와 draw call 수는 비례하지 않는다.
- 멀리 있는 적과 가까운 적의 업데이트 빈도를 분리한다.
- F3 디버그 오버레이에는 적 수, FPS, 시뮬레이션 틱 시간(이동·전투·그리드·Flow 단계별), 렌더 시간, 유입률, 공간 그리드 상태를 노출한다.

### 물량 단계와 성능 목표

물량은 단계적으로 올린다. 각 단계에서 시뮬레이션 틱 시간과 렌더 시간을 분리 측정하고, 병목을 확인한 뒤 다음 단계로 간다.

| 단계 | 목표 | 성격 |
| --- | --- | --- |
| 100 | 구조 동작 확인 | 시뮬레이션·렌더러 분리와 재현성 검증 |
| 500 | 안정적인 60fps | 재미 증명 기준 물량 |
| 1,000 | 안정적인 60fps | 화면이 무리로 읽히는 첫 규모 |
| 5,000 | 플레이 가능한 성능 (평균 30fps 이상, 틱 30Hz) | 병목 측정 후 필요한 부분만 최적화 |
| 10,000 | 최종 확장 목표 | 틱 30Hz 유지, 렌더 60fps |
| Flow Field 재계산 | 체감 가능한 프리즈 없음 | 모든 단계 공통 |

기준 하드웨어는 검증 계획에서 정한다. 목표에 못 미치면 렌더 품질보다 시뮬레이션 틱 분산과 업데이트 빈도 조정을 먼저 시도한다.

### 측정 기록

병목을 찾고 대응한 결과를 시간순으로 남긴다. 수치는 headless 회귀·소크 기준이다.

| 날짜 | 병목 | 측정 | 대응 | 결과 |
| --- | --- | --- | --- | --- |
| 2026-09-25 | Flow Field 전체 재계산 | 128×128 한 번에 약 37 ms (BFS 7 ms + 방향 30 ms). 건설 직후 500마리 스트레스 최악 틱 45.8 ms | 뒤쪽 버퍼에 BFS 4,096셀·방향 2,048셀씩 틱마다 진행하고 끝나면 교체. 방향 계산의 8방향 루프를 펼치고 c−2 대각선에서 조기 종료 | 틱당 약 1.5 ms, 전체 약 12틱(0.4초) 분산. 500마리 최악 틱 2.8 ms. 결과 필드는 기존 계산과 셀 단위로 동일 |
| 2026-09-25 | 물량 단계 측정 (1,000 → 10,000) | `tools/tests/stress_scale.gd`(headless, 틱 단계별)·`render_stress.gd`(창 모드, 수직 동기화 끔). 타워 90개 링, 살아 있는 적 수를 N으로 유지. 틱 평균: 1,000 0.9 ms / 5,000 4.0 ms / 10,000 7.8 ms, 이 중 적 이동이 약 60%. 창 모드 FPS: 1,000 243 / 2,000 169 / 5,000 112 / 8,000 78 / 10,000 72 | 적 렌더 버퍼를 상한(8,192×타입 4)이 아니라 실제 물량에 맞춰 두 배씩 늘림(시작 512). 적 상한 8,192 → 12,288 | 단계 D 목표(1,000 60fps, 5,000 30fps)와 10,000 틱 30Hz·렌더 60fps를 개발 PC에서 충족. 남은 것은 대량 사망 순간 프레임 최악값(5,000에서 약 22 ms, 10,000에서 약 35 ms) |

### C++은 출발점이 아니라 탈출구

처음부터 C++로 만들지 않는다. 순서는 아래와 같다.

```text
Godot + GDScript + 좋은 데이터 구조
        ↓
    Profiler
        ↓
    병목 발견
        ↓
정말 필요한 부분만 C++ GDExtension
```

GDExtension 검토 조건: 틱 분산, 업데이트 빈도 LOD, 배열 연산 최적화를 모두 시도한 뒤에도 해당 단계의 목표에 못 미칠 때. 옮기는 범위는 측정으로 확인된 핵심 루프(예: Flow Field 전파, 적 이동 적분, 근접 탐색)로 한정한다.

## 대량 전투 피드백

타격감은 개별 공격이 아니라 대량 전투를 기준으로 만든다. 기술적으로는 “이벤트를 하나씩 재생”이 아니라 “틱 단위로 모아서 규모에 비례해 재생”이다.

- Combat Sim은 틱마다 처치 수, 처치 위치 중심, 폭발 반경별 처치 수를 집계해 이벤트 큐에 넣는다.
- GameFeel은 틱 처치 수에 비례해 흔들림 강도와 히트스톱 길이를 정한다. 개별 처치마다 흔들지 않는다.
- AudioManager는 처치 수 구간별로 사운드 레이어를 쌓는다. 동일 사운드 동시 재생 수는 상한을 둔다.
- Renderer는 처치 이펙트를 위치 기준으로 병합하고, 프레임당 이펙트 생성 수에 상한을 둔다.
- 포격 폭발은 반경 안의 적이 같은 프레임에 사라지게 한다. 처치가 틱에 걸쳐 흩어지면 폭발감이 사라진다.

## 데이터 관리

게임 밸런스 데이터는 코드에 흩어지지 않게 정리한다.

- 건물 데이터: 비용, HP, 크기, 철거 회수율. 타워는 사거리, 공격 주기, 피해, 광역 반경, 감속량
- 적 데이터: HP, 속도, 공격력, 보상, 분열 규칙, 스프라이트 기준
- 압박 데이터: 바닥 유입·목표 무리 수 곡선, 배율·변 가중치 범위, 적 구성 비율, 개체 강화 배율 (Wave Sim 상수)

Godot Resource를 기본으로 쓰되, 반복 튜닝이 필요한 값은 한곳에서 찾을 수 있어야 한다. 시뮬레이션은 Resource를 직접 들고 다니지 않고 시작 시 테이블로 펼친다.

## UI와 정보 구조

HUD는 첫 프로토타입에서 최소로 유지한다. 우선순위는 아래와 같다.

1. 본진 위험
2. 지금 두꺼운 방향과 유입률
3. 미네랄과 건설 가능 여부
4. 선택 중인 건물의 효과
5. 미니맵 또는 레이더의 스폰 방향과 누수 지점

2D 쿼터뷰에서의 가독성 원칙:

- 적 타입은 실루엣과 색으로 구분한다.
- 밀도는 개체 겹침 자체로 표현한다. 겹침을 피하려고 스폰을 줄이지 않는다.
- 방어선 붕괴 지점은 건물 파괴 이펙트, 레이더 표시, 카메라 반응이 같은 위치를 가리켜야 한다.

UI는 플레이어가 “왜 죽었는지”와 “다음에 무엇을 바꿔야 하는지”를 이해하게 해야 한다.

## 저장과 통계

런 중 세이브는 핵심 범위가 아니다. 우선순위는 런 종료 통계와 설정 저장이다.

- 개인 최고: 생존 시간, 처치 수, 최대 동시 적 수, 런 횟수 (`user://records.cfg`, GameManager가 관리)
- 런 요약: `GameSimulation.run_summary()`가 결과 화면 재료(뚫린 쪽, 지은·잃은 건물, 쓴·남은 미네랄)를 만든다. 시뮬레이션은 계산만 하고 저장은 표현 계층이 한다
- 설정: 언어, 볼륨, 해상도, 전체화면

## 보류 시스템의 재도입 지점

보류 시스템을 미리 구현하지는 않지만, 재도입할 때 어디에 붙는지는 정해 둔다.

| 시스템 | 재도입 지점 |
| --- | --- |
| 유닛·배럭 | Combat Sim에 유닛 배열 추가. 적과 같은 배열 구조, 타겟팅은 Spatial Grid 공유 |
| 레벨업 | BuildingData에 단계별 수치. 건물 Node가 Combat Sim의 타워 테이블을 갱신 |
| 시너지 | Combat Sim의 피해 계산 한곳에 배율 테이블 조회를 끼운다. 카운트 계산은 Autoload |
| 보상 카드 | 웨이브 완료 지점이 없으므로 시간·처치 수 기준 정지 사유를 Game Simulation에 추가. 선택 결과는 배율 테이블·건물 해금으로 반영 |
| 이벤트·정예·보스 | Wave Sim 입력에 배율과 정예 슬롯 추가. 큰 개체는 Renderer에서 별도 레이어 |

| 리스크 | 대응 |
| --- | --- |
| GDScript 시뮬레이션이 목표 물량에 못 미침 | 틱 분산, 업데이트 빈도 LOD, 배열 연산 최적화를 먼저 한다. 그래도 부족하면 측정으로 확인된 핵심 루프만 GDExtension으로 옮긴다 |

| 보류 시스템을 미리 만들고 싶어짐 | 재도입 지점만 문서로 정하고 코드는 넣지 않는다 |
| 문서와 구현이 어긋남 | `docs/game-design.md`와 `docs/quality-plan.md` 기준으로 변경 검토 |
